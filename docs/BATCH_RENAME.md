## 2000 个文件的操作流程

1. 打开一个目录，一次选择 2000 个文件，配置最多 20 条规则。
2. 点击“刷新预览”：显示超过 1000 项的分批提示 Dialog（可勾选“下次不再提示”）；取消不开始任务，点击“继续预览”才创建任务并保留全部 2000 项快照，仅向后端提交前 1000 项。
3. 检查预览及冲突；点击“开始修改”，在 Dialog 中点击“应用”。
4. 后端复核快照并执行本批。前端根据逐项结果记录状态；全部成功时已完成为 1000，待处理为 1000，并保留后 1000 项选择。不自动刷新目录，仅合并执行结果中已确认的文件元数据。
5. 当前任务面板默认勾选“待处理”，只显示待处理成员；通过原筛选菜单调整状态，再用表头选择剩余项目，点击“刷新预览”生成第二批预览。
6. 再次检查预览并确认执行。全部成功时已完成为 2000、待处理为 0。

部分失败时，失败项与其他批次记录都保留。默认待处理筛选使失败项退出当前选择，但记录保留；失败项可在“失败/待核对”筛选下单独选择并重新预览。不存在无人值守连续执行。

若执行请求丢失完整响应或返回不确定结果，本批相关条目锁定。先在真实目录人工核对文件身份及实际执行结果；本轮按交互要求移除核对弹窗，未知项不能在当前任务直接重试。使用 Logout 结束旧任务，再根据核对结果重新选择。界面不读取文件内容，也不按名称自动推测成功。

全批无名称变化时仍可点击“开始修改”并确认；后端复核后返回 skipped，任务才将这些项记录为完成。

## 限制与兼容性风险

- 跨批次名称依赖不调度。例如本批 A→B，而 B 属于未处理批次，预览会报告冲突并拒绝执行；不能强制跳过检查。用户可调整批次选择/规则并重新预览。
- 现有四种规则没有使用 RuleContext.index/total 生成序号。未来新增序号规则必须先明确全任务顺序和总量协议，当前没有跨批次序号功能。
- 任务文件集合在首次预览时固定。新增选择需显式重新开始任务；规则变化后不能直接继续旧批次，重新预览会以剩余选择创建新任务。Logout 结束任务会清空选择和旧会话记录。
- 切换连接、目录、账号或连接版本会结束任务并清除选择。页面刷新也会丢失任务；本阶段不保证跨页面会话的完成项去重。
- 外部删除/移走的项不被标记为完成，但可能仍计入任务待处理数；只有实际存在于当前目录的身份可继续预览。无法确认身份的未知项保持锁定，不按名称自动修复。
- 仍一次加载整个目录，未增加分页、虚拟化或缓存同步；大目录渲染和筛选菜单需要人工性能验收。
- execute 的输入、原有逐项状态、错误码、快照复核和回滚语义保持。current_file 为新增可选字段，原 file_id 仍表示执行前请求身份；前后端应同步部署，以可靠跟踪 Local 新路径 ID。
- 新的 1000 文件/20 规则上限会拒绝原先可提交的更大单批请求；完成任务条目（包括 skipped）不再进入同一任务的后续批次。其余原有单批确认交互保留。

## 实际保存与未来扩展

任务中目录查询暂停自动读取，包括焦点/重连、缓存失效及执行结束；保留手动刷新。执行进度的只读轮询与连接状态查询继续保留，后端预览/执行安全复核也不受影响。

本次实际保存在前端内存中的数据：任务 ID、批次 ID、预览 ID、存储连接和位置、上下文（含连接版本和规则）、规则副本、taskItemId、原选择顺序、before 原始文件快照、currentFileId、after 最后执行结果、各批逐项返回结果、批次未知标记，。人工核对结构与 Store 方法保留，但当前没有交互入口，正常任务不会写入人工核对数据。before 不覆盖；重试的旧结果保留在各批 results 中。

服务端仍保存原有短期预览快照和进度，未新增任务数据库或历史持久化。现有 TanStack Query 目录缓存继续用于展示，不作为执行凭证。

提示偏好实际保存到浏览器 localStorage（renamer-hide-batch-limit-hint）；会话任务仍不持久化。

仅类型预留的数据：FileSnapshot.version。当前 Provider 尚未填充版本标识。没有空缓存管理器、空撤回服务或额外后台服务。

未来快照缓存需要独立定义连接/目录/账号/版本的缓存键、失效和同步策略，并由后端决定哪些元数据可以安全复用；客户端缓存不能替代执行前复核。

未来撤回需要服务端持久化实际操作历史及成功前后身份、名称和结果，提供独立的撤回预览/确认 API，复核当前身份、权限、外部变化及名称占用，复用安全执行/回滚语义。当前会话记录不能视为正式撤回历史。
